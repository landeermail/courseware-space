# ADR 0004：固定 K3-256K 为课件生成模型

- 状态：适用范围已收缩；仅在明确恢复既有生成 harness 时重新核验，默认研发实验不适用（ADR 0011）
- 日期：2026-07-29
- 演进：ADR 0002（本地 MVP 使用 Kimi Code）

## 背景

项目最初使用 `kimi-for-coding`（Kimi K2.7 Code）完成本地 MVP 和导体杆模板验证。Kimi Code 后续提供 K3、K3-256K 与 K2.7 HighSpeed。课件生成的主要经济指标不是单次请求成本，而是每份最终验收合格课件的总成本；模型能力不足造成的重试、拒绝和人工返工同样会侵蚀盈利能力。

单题课件的题目、确认参数、物理契约和完整页面生成均远低于 256K 上下文。K3 的 1M 上下文当前没有实际收益，官方说明它约消耗 K3-256K 两倍额度。HighSpeed 与对应常规模型能力相同，只缩短等待时间并显著提高额度消耗，不符合当前“不缺时间、优先控制成本”的约束。

## 决策

- 生产生成服务与课件生成 harness 统一使用常规速度模型 `k3-256k`。
- 所有调用显式固定 `reasoning_effort=high`；建立稳定基线前不允许使用 `low` 或 `max`，也不依赖供应商可能变化的默认值。
- 不允许通过环境变量临时切换模型；模型 ID 由代码白名单固定，变更必须经过明确的产品与成本决策。
- `k3` 暂不启用，因为当前不需要 1M 上下文。
- `kimi-for-coding-highspeed` 持续禁止；既有 HighSpeed 结果只作为历史诊断证据保留。
- K3-256K 不可用时失败关闭，不自动降级到 K2.7、1M K3、HighSpeed 或其他模型；备用模型必须独立完成质量与成本验证并形成明确决策。
- `temperature` 与 `top_p` 不显式发送，固定使用供应商默认采样策略；证据记录为 `provider_default`，部署环境不能覆盖。累计 30 道后只有在观察到实际波动时才另做受控实验。
- 套餐额度或五小时频限耗尽时立即停止模型调用，转稍后重试或人工处理；Kimi 账户层保持 Extra Usage 关闭，不允许自动付费续跑。
- 一个生产任务只共享一次临时网络或服务错误重试额度；额度、频限、鉴权、权限和配置错误不重试。重试上限由代码固定，不能通过部署环境放宽。
- 文字与视觉解析等待上限为 120 秒；物理模型和完整教学页面使用流式响应，网络静默上限为 300 秒。请求发出后的读取超时不自动重试；只有明确的连接建立失败或 HTTP 5xx 可占用共享重试额度。云函数运行上限必须高于模型等待上限。
- harness 分为研发验证与生产交付两种固定模式。研发尝试完整保留失败→修正链并用于改进通用护栏；生产只做有限后台自愈，不要求用户反复重新提交。
- 研发验证模式的物理模型阶段和教学视图阶段各最多尝试 3 次；第三次仍失败就停止调用，进入人工根因分析。harness 改版后使用新版本和新运行记录，不覆盖原失败链。
- 生产交付模式的物理模型阶段和教学视图阶段各最多尝试 2 次；首次失败后仅允许一次携带机器反馈的后台修正，第二次仍失败就转人工。用户只提交一次，一份课件最多进行 4 次内容生成调用。
- 生产单题入口的 PDF 最多 2 页；研发验证可显式处理最多 6 页且单独记账。整卷批量解析与建课件留作独立计费产品，不复用普通单题额度。
- 开发阶段不新增图片像素、压缩率或模型前重编码规则，沿用现有文件格式与上传大小校验；只有真实证据表明大图造成明显识别失败或额度浪费时再另行决策。
- 建立持久化模型调用预算账本：每次真实 provider 尝试前先占用额度，按调用用途记录，生产与研发分账；达到单任务上限时在发出请求前停止，服务重启不能清零。
- 部署环境只能把预算设得更低，不能突破代码中的安全上限；账本关联最终验收状态，以计算每份合格课件的实际调用数。
- 生产单任务最多进行 7 次真实 provider 请求：最多 2 次输入理解、物理模型和教学视图各 2 次、全任务共享 1 次临时故障重试。达到上限后转稍后处理或人工处理。
- MVP 阶段账本先测量而不设置任意应用级日/月数字；完成 30 道独立生产式任务后制定临时预算，完成 100 道独立盲测后确定商业容量与定价。Extra Usage 关闭期间，供应商套餐额度继续作为阶段性总上限。
- 调用账本记录任务/模式/阶段/尝试、请求与实际模型、推理档位、输出上限、响应 ID、结束原因、供应商返回的 token/缓存/推理用量、延迟、错误分类和最终验收状态；缺失字段留空。生产账本不保存 API Key、原题正文、媒体内容、隐藏推理或供应商错误正文。
- MVP 阶段所有文字解析、视觉解析、物理模型和教学视图共用全局串行队列，模型调用并发固定为 1，部署环境不能提高；外部试用后凭排队时间和单位成本数据重新决策。
- K3-256K 研发输出上限固定为：文字/视觉解析 16,384 completion token、物理模型 32,768 token、教学视图 65,536 token；`model_js` 可见字符上限保持 30,000，HTML 从 120,000 收紧为 96,000。长度截断只记录、不自动重试；首批 10 道只观察，累计 30 道后再制定生产上限。
- 所有模型阶段固定发送 `response_format={"type":"json_object"}`；本地契约继续验证字段和物理语义。研发阶段暂不启用 JSON Schema，且不允许通过部署环境关闭 JSON Mode。接入 K3-256K 时先做能力探针，不支持则明确失败，不静默回退无约束文本。
- 每个任务按提示词版本和阶段使用不含业务内容的稳定 `prompt_cache_key`；同一阶段的首次生成与反馈修正复用，物理模型与教学视图隔离，新任务不跨用户复用。模型、推理档位或提示词版本变化时更换键。
- 私人研发阶段允许现有供应商账户内逻辑分账；任何外部用户接入前，生产与研发必须迁移到真正独立的账户和额度池。生产凭证只部署到云端，研发凭证只供开发电脑与 harness 使用；同一账户下的不同 API Key 不视为额度隔离。
- Kimi Code 仅用于当前私人研发与演示。对公众开放或收费前，必须迁移 Kimi Platform，或者取得 Kimi 对产品后端用途的明确书面许可；届时重新确认模型、计价、预算和利润率，研发期的 `k3-256k` 决策不自动延伸为商业生产许可。
- MVP 前不实现预览访问码或用户系统；Extra Usage 关闭、单任务调用上限、额度错误停止、现有并发与频率限制构成当前最小保护。主动邀请外部老师、公开生成入口、启用按量付费，或匿名调用实际影响研发额度前，访问控制成为强制上线门槛。
- 用于提示词、原语、契约或断言改进的题目立即归入开发集，不能继续计入独立盲测；模型与 harness 的市场成熟度必须用未参与调优的新题验证。
- 模型经济性按“每份验收合格课件的总模型调用与返工成本”评估，而不是只比较单次请求消耗。

## 结果

- 新模型能力预期可减少自由代码生成中的返工，但仍必须由物理断言、沙箱与老师验收兜底，不能把模型升级等同于质量保证。
- 项目需要把客户端、harness、回归测试和部署说明从 K2.7 更新为 K3-256K，并在额度恢复后重新建立真实生成基线。
- 如果后续证据表明 K3-256K 的合格产物成本反而更高，应以新的 ADR 调整模型，而不是通过部署变量静默回退。
- 额度耗尽会降低短期可用性，但把最大现金支出变成可预测的订阅成本；未来商业化若启用按量付费，必须另行制定生产预算与熔断决策。
- 研发模式会有意消耗更多调用来换取可复用的失败知识；这些调用必须单独记账，不能混入生产单位经济性。
